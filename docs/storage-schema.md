# Browser Storage Schema

The browser storage implementation is spread across the owner modules below; there is not yet a single runtime key registry. This page is the inventory of keys currently read or written by the application. `localStorage` values survive browser restarts. The two `sessionStorage` values are short-lived workflow handoffs and are listed separately.

## localStorage keys

Unless noted otherwise, JSON values are encoded with `JSON.stringify`. Keys owned by `lib/storage.ts` use the storage schema version in `txwatch_storage_version`; preferences, sync state, notifications, and wallet state are currently unversioned and must remain backward compatible or be migrated explicitly.

Do not put a webhook signing secret or other credential in browser storage; localStorage is readable by same-origin JavaScript.

## sessionStorage workflow keys

These values are scoped to a browser tab session, are not part of the versioned localStorage schema, and are removed after consumption where applicable.

| Key                             | Stored shape                                                                                                                                               | Owner                                                             |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| `txwatch_duplicate_contract`    | JSON object with optional `label: string`, `webhook_url: string`, and `rules: AlertRule[]`; consumed to prefill the duplicate-contract form, then removed. | Contract detail duplicate action and `app/contracts/new/page.tsx` |

## Limits and cleanup

- Alert retention defaults to 90 days. Saving a retention setting prunes entries older than that setting.
- The normal `addAlert` path keeps at most 500 alerts per `(contract_id, network)` by dropping the oldest. Bulk alert replacement/import does not pass through that cap.
- Storage size is estimated by summing key and value string lengths at two bytes per UTF-16 code unit. When the estimate exceeds 90% of the 5 MiB target (about 4.5 MiB), alert writes are reduced to the latest 30 days; a non-alert write also triggers a best-effort trim of existing alerts to 30 days.
- If a write throws a recognized quota error, the storage layer prunes using the configured retention period and retries that write once. Other storage failures return/fall through as best-effort failures. The browser's actual quota varies, so these are safeguards, not a guaranteed allocation.

## Migrations

`CURRENT_STORAGE_VERSION` is defined in `lib/storage.ts`. Migrations are registered in `lib/migrations.ts` by the version they upgrade **to**, and `components/StorageBootstrap.tsx` runs them at startup. Version `0` is unversioned legacy data; v1 is the compatible baseline, and v2 backfills `enabled: true` on contracts.

When changing a persisted shape:

1. Update the owning TypeScript type, storage validation/read/write code, and any import/export representation that includes the field.
2. Add a migration function in the owning storage module (or a focused helper), then register it in `lib/migrations.ts` under the next version number. Make it safe for existing and already-partially-upgraded data.
3. Increment `CURRENT_STORAGE_VERSION` in `lib/storage.ts` to that same number. Add a migration test covering old data and the resulting shape; keep the contiguous-version test passing.
4. Update this inventory, including the key's owner, shape, version, defaults, and any changed limits. Verify import/export and consumers that read the stored value.

Every version from `1` through `CURRENT_STORAGE_VERSION` should have a registry entry. Do not rewrite or remove an old migration: existing browsers need the full upgrade path. Migrations run synchronously, so keep them bounded and avoid network access.

## Known schema drift to resolve

- `WatchedContract` in `types/index.ts` currently omits `enabled`, even though storage writes it and migration v2 backfills it. Keep the type and persisted contract shape aligned when touching this field.
- The contracts page and `lib/contractSort.ts` both use `txwatch_prefs` but accept different `sortBy` values. Reconcile those consumers before expanding the preference schema.
- `components/RetentionSetting.tsx` currently previews old-alert counts by reading the literal key `alerts`, while the canonical alert array is `txwatch_alerts`. That read is not a persisted schema key and does not count the canonical history.

There is currently no webhook-secret key in browser storage. If that changes, document its security and backup/export behavior explicitly before adding it.
